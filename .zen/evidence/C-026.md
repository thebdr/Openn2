# C-026 - Files tab: no silent discard of unsaved edits - evidence

## Origin (2026-09-26, C-025 refute round 4)
The C-025 refuter's discard probe found Files-tab gaps that predate the template builder. They were routed
out of C-025's clause into a task of their own:
1. The Text <-> Object explorer toggle (`flip` -> `_load`) dropped the text pane's unsaved edits, the template
   mode's included, without asking.
2. `FilesPanel._unsaved_changes()` never consulted the Object explorer's own dirty flag: picking another file
   dropped Object-explorer edits without asking.
3. `FilesPanel.set_theme` reloaded a shown CSV/xlsx: a dirty CSV grid lost its cell edits without asking.
4. (the safe direction) the text pane stayed modified after undo / redo / cut back to the saved text, a needless
   question. C-025 round 3 re-arms Tk's modified flag on every edit, so Tk's own undo accounting no longer tells.

## Spike (2026-10-05) - the real FilesPanel on an off-screen Tk root, at 62bcc15
Driven through the real widgets (Tk 8.6.15, Python 3.14.4), `messagebox.askyesno` patched to answer No:
- gap 1: a typed edit in project_params.yaml, then the "Object explorer" radio invoked -> no question; the
  Object explorer was shown; the edit was gone.
- gap 2: an Object-explorer value committed (`_dirty` True), `_unsaved_changes()` False; another file picked in
  the tree -> no question; the other file shown.
- gap 3: a committed CSV cell (`_csv_dirty` True), then `set_theme("light")` -> no question; a NEW grid;
  `_csv_dirty` False; the edit gone.
- gap 4: confirmed - and the spike found a WORSE fifth: the load's own `insert` sat on the undo stack (the text
  is built with `undo=True` and the stack was never reset). One Ctrl+Z (`<<Undo>>`) right after opening a file,
  with NO edit, EMPTIED the pane and set it modified - Save (enabled) would have written the empty file. An edit
  + one undo emptied it too (the load and the edit were one undo group). The same in the template mode: an
  emptied templates.yaml, Save one click away.

Tk facts the fix relies on (observed, not assumed):
- the text widget round-trips a non-BMP character and U+2028 exactly (`get` returns what `insert` took);
- `selection set` on the already-selected tree item still fires `<<TreeviewSelect>>` (the rollback flag of the
  tree-pick guard is always consumed); deleting the selected item fires none;
- the cost of a full-text comparison: `text.get` 0.3 ms at 0.1 MB, 3.8 ms at 2 MB, 53 ms at 20 MB (the editor
  cap is 50 MB) - too slow per keystroke on a big file, so the modified mark is set at once on an edit and
  re-checked after a pause, while the discard guard compares exactly at the moment it asks.

## Design (the clause's intent, how it landed)
- ONE guard - `FilesPanel.confirm_discard()` - for every path that replaces or closes the shown viewer: the
  tree pick (rolls the selection back on No), the Text <-> Object toggle (the toggle snaps back; clicking the side
  already shown is a no-op - it used to reload), the project-copy jump (`_reveal`'s direct load), and the App's
  close (`App._on_close` - not in the routed list; the same silent loss, found while enumerating the paths).
- `_unsaved_changes()` = the CSV grid's flag OR the Object explorer's (`ObjectEditor.dirty` - a public read-only
  property added to FileXY's objectview, so the host never reads a private field) OR the text pane's: the
  cheap flag AND an exact comparison of the text with the saved text, computed when asked.
- the saved text = the widget's own `get` right after the load (and the text written at each Save); the load is
  not undoable (`edit_reset` after the insert).
- `set_theme` re-themes IN PLACE: the text pane as before, every DataGrid under the editor (`DataGrid.set_theme`
  already existed), the Object explorer (`ObjectEditor.set_theme` - added: its row tags and dividers were fixed
  at construction, although set_theme's own comment claimed the object view re-themes in place).
- Revert stays the deliberate discard (no question) - text, CSV and the Object explorer's own Revert alike.
- the tree pick's No rolls the selection back to the shown file's item, found by a normalized lookup
  (`_item_of`, shared with `_reveal`) - or to NO selection when no section lists it any more (a project / system
  switch re-sections the tree): the old loop compared the strings exactly and, finding nothing, left the
  unopened pick selected beside the edited file. The rollback's own `<<TreeviewSelect>>` is still skipped by the
  `_reselecting` flag (Tk 8.6.15 raises it on every `selection set`, the spike).

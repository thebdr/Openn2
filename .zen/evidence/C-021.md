## 2026-07-16 — architecture-rules literature sweep (10-agent workflow, adversarially verified)

Trigger: the user rejected the inherited layer-first structure ("not suited for a big, growing
project") and asked for public-domain literature to ground an adoptable rule set. Pains (user-ranked):
flat growing `domain/` · no enforced boundaries · unclear entry/ownership. NOT primarily the
kernel/gui layering itself. Additional user inputs: GUI–code match is desirable; phases WILL be added
(identifier stability matters). 5 research briefs + 5 adversarial attribution checks (4 accurate,
1 minor: Shopify's Wedge computed isolation scores/violation lists rather than failing CI — Packwerk
later hardened this; a Gebski article date). Sources are primary where possible.

### What each school contributes (and what we reject)

**Clean/Onion/Hexagonal (Martin 2012 · Palermo 2008 · Cockburn ~2005).**
ADOPT: the Dependency Rule (inward-only source dependencies); headless operation (the app drivable
without the GUI — already true); ports only where MULTIPLE adapters genuinely exist (the System
descriptor is a real port: N target systems). REJECT: ring ceremony and interfaces-for-single
-implementations — the documented indirection tax (Comartin: "you're still just as coupled, but with
more indirection"; change-amplification and onboarding-cost critiques). PL4/PL5's concrete style is
deliberately kept.

**DDD + Modular Monolith (Evans · Brown's package-by-component · Shopify).**
ADOPT: package-by-component (a component owns everything its capability needs behind one public
interface); ubiquitous language (the operators' phase numbers/buttons ARE the domain language);
bounded contexts (the platform→toolchain→system taxonomy is a context map; Evans explicitly warns
against total unification — the user's "hand-authored ports, no real cross-platform" instinct is
Evans-correct); Brown: unenforced boundaries are cosmetic — enforcement must be mechanical.
CAUTION: wrong boundaries drawn early are the expensive mistake (Shopify's multi-year untangling).

**Package-by-Feature / Vertical Slices / Screaming (Hauer · Bogard · Martin).**
ADOPT: the deletability test (deleting a capability = deleting exactly one package); Bogard's growth
rule ("new features should add code, not modify shared code" — the direct answer to "we will be
adding phases"); the structure announces the DOMAIN (the pipeline), not the framework; `common`/
`shared` only after the Rule of Three and watched for regrowth. CAUTION: duplication-across-slices
is the documented failure mode at scale; cross-cutting concerns need one home.

**Pipes-and-Filters + Microkernel (POSA1 Buschmann et al. 1996 · Richards).**
ADOPT (P&F): filters unaware of neighbors, communicating only through the data stream — for PL5 the
stream IS the SSOT database; no shared state between stages outside it; per-stage error policy (the
severity/gate model already is this). ADOPT (Microkernel): minimal general core with NO
system-specific conditionals; volatile/custom logic in independent plugins; registry-only discovery;
CONTRACT VERSIONING from the start (a `schema_version` on the System contract). HEED: the core/plugin
boundary mistake is the expensive one; POSA calls mid-pipeline error handling the Achilles' heel
(the findings/gate model + chain_reactions_log answer it).

**Python practice (PyPA src-layout · PEP 8 · Django apps · import-linter/Kraken · tach).**
ADOPT: import-linter contracts run by the test gate — layers (no upward import, even indirect) +
independence (sibling packages must not import each other), the Kraken pattern (40+ contracts over
27,637 modules, 400 devs — the existence proof that convention-only decays and contracts scale);
ratchet unavoidable legacy violations via a shrinking ignore list. DEFER: src/ layout (PyPA frames it
as a packaging-honesty trade-off aimed at distributed libraries; PL5 is a deploy-only desktop app —
revisit at the v1.0 packaging step). NOTE tool scope: contracts see static imports only.

### The proposed rule set (R1–R7, each attributed)

- **R1 Components, not layers** (Brown; Hauer; Bogard): one package per pipeline capability owning
  its logic + schema + projections + tests. Deletability test holds; adding a phase adds a package.
- **R2 Phases are filters** (POSA P&F; Kraken independence): pipeline components may NOT import each
  other — they communicate exclusively through the SSOT tables. Cross-phase domain helpers live in
  ONE small shared package, admitted only on the Rule of Three.
- **R3 One dependency direction** (Martin/Palermo; Seddon layers): kernel ← pipeline ← (systems,
  shell); no upward import, even indirect.
- **R4 Microkernel plugins** (Richards): the core stays general — no system-specific code or
  conditionals (capability flags, not type-ids); systems are independent plugins discovered only via
  the catalog; the System contract carries a version from day one.
- **R5 Machine-enforced** (Brown; Kraken; Shopify's lesson): R1–R4 exist as import-linter contracts
  executed by the test gate — violations are red builds, not review comments.
- **R6 Public API per component** (Brown; tach): outsiders import the package, not its internals;
  the signpost `__init__` IS the declared API.
- **R7 Stable identifiers, registry-bound language** (Evans; user's GUI-code match + phase-growth
  concern): folders carry stable domain slugs; the operator phase NUMBERS live in exactly one place
  (the phase registry), which binds number ↔ button ↔ component ↔ clause ↔ tests. Renumbering or
  inserting a phase = a registry edit, zero folder churn.

### The two tree variants (decision OPEN — the user is reflecting)

A (recommended): `pipeline/{staging, fillout, validation, changes, interfaces, io_tags, datablocks,
diagnosis, hardware, software_blocks, coverage, chain_reactions, shared}/` — stable slugs, numbers in
the registry (R7). B: `pipeline/phNNN_*` numbered folders — maximal visual match to the operator
oracle, at the cost of folder churn when phases are added/renumbered (the user's own concern).
Both keep: `kernel/` (foundation), `systems/` (plugins), `shell/` (GUI adapter + project manager).

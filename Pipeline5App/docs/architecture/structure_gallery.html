Eight truths every choice must face

The critics converged on the same real coupling in today's code — these get solved under any winner, so they are the actual work list of the restructure:

The GUI is the secret orchestrator

app_main's phase handlers chain staging → 520 → 400 → … per button; every candidate must extract this run-plan out of Tk code into a registry/composition root before any phase-independence law can hold. (Found by the components + slices critics.)

signal_coverage imports three sibling phases

It calls functions of datablock_generator, diagnosis_builder, interface_builder (seed_members(), TRIGGER_TYPE, node_of). Coverage must be re-plumbed to read the SSOT tables it audits — the exact spirit of the phases-are-filters law. (stream critic, verified lines.)

validation_runner re-runs staging

domain/validation/validation_runner.py literally calls staging.stage(params) — the validate phase re-executes another phase. Either validation consumes staged tables, or staging exposure becomes a kernel service. (stream + manual critics.)

cematrix_annotation is not a standalone phase today

staging calls annotate() inline; the oracle 310/320 split exists at the API, not in module independence. Any candidate that separates them must accept the edge or merge the folder. (stream critic.)

Table schemas live inside builder modules

interface/hardware/block tables are defined in the modules that write them; several phases import a sibling just for its schema. Every candidate converged on the same cure: a data dictionary — schemas owned centrally (stream/truth/shared-tables) or fetched by name from the SSOT registry. (all five critics, various forms.)

software_blocks ↔ Siemens emitters are one cluster today

build_engine imports datablock_xml + builders/scl_emit/xml_emit directly; until step 4 moves them behind system.emitters, every candidate needs a declared, shrinking allowlist for these edges. (slices + manual + hexagon critics.)

finding ↔ report_model ↔ report_renderer form a mini-cycle

finding imports Cmp/InfoBlock from report_model while report_renderer imports finding — any layering of 'findings' vs 'reports' must keep them in one layer or split the value objects. (manual critic, verified lines.)

Import-side-effect registries are fragile

Check/table registration at import time only works if the composition root imports everything first; headless runs and tests bypass it. Registration must be explicit (called, not import-triggered) whatever the shape. (components critic.)

The laws (each an import-linter contract)

  • LAYERS (import-linter 'layers'): app → gui → project → systems → components → kernel; each layer imports only layers below it. Kernel at the bottom, composition root at the top — one dependency direction, no exceptions.
  • COMPONENT INDEPENDENCE (import-linter 'independence' on pipeline5.components.*): components never import each other — not even each other's schema modules. Data crosses component boundaries only as SSOT tables fetched by name from kernel.ssot.database's registry. This is the pipes-and-filters constraint made a static import contract.
  • COMPONENT PRIVACY (import-linter 'forbidden', one per component or wildcarded): from outside a component, only pipeline5.components.<x> (its __init__ public API) and components.<x>.ui may be imported; components.<x>.* internals are forbidden to gui, systems, and app alike.
  • KERNEL PURITY (import-linter 'forbidden'): pipeline5.kernel imports nothing from pipeline5 outside kernel, and never imports tkinter. kernel.vocab is part of kernel and bound by the same law — it can never grow upward dependencies.
  • HEADLESS PIPELINE (import-linter 'forbidden' with narrow exception): pipeline5.components.* and pipeline5.systems.* never import tkinter or pipeline5.gui — except a component's dedicated 'ui' submodule (e.g. components.diagnosis.ui), which only the gui shell may import, discovered via the registry.
  • PLUG DIRECTION (import-linter 'forbidden'): pipeline5.components.* never import pipeline5.systems. Systems implement component-owned sockets (software_blocks.sockets pattern) and are wired exclusively in app/wiring.py via systems.catalog; systems may import components' public APIs and kernel.
  • SYSTEM ISOLATION (import-linter 'independence' on pipeline5.systems.<platform>.<toolchain>.*): system plugins never import one another — siemens_s7 and intervalzero_rtx share only kernel and component public APIs.

The critic's verdict — breaks (9) and strengths (8)

Breaks found (code-grounded)

  • Schema-registration-at-import collides with project-parameterized schemas (VERIFIED): signals_table(iolist_columns) builds its column list from the project's colmap at every one of its 10 call sites (e.g. pipeline4/domain/datablocks.py:275, staging.py:304). A component cannot 'register the schemas it owns at import' because the signals schema does not exist until a project is open and load_column_map has run. The registry needs a factory-registration + resolve-at-project-open lifecycle the candidate never specifies, and db.table('signals') is undefined during the import-time window app/wiring.py relies on. This complicates exactly the move the candidate calls 'the largest single decoupling'.
  • Component UIs have no legal access to shared tkinter widgets — a module with no honest home: law 5 sanctions components.<x>.ui as the one tkinter spot inside a component, but the LAYERS law forbids components importing gui, so components.diagnosis.ui cannot import gui/widgets/datagrid.py, object_editor.py, or theme.py. Widgets cannot sink to kernel either (KERNEL PURITY: never tkinter). Every capability panel will want the datagrid; the structure forces either duplication, runtime injection of widget classes (invisible to the linter), or a law violation. The growth story's 'bespoke tool lands as components/<x>/ui.py' breaks on its first real panel.
  • The pipes-and-filters contract becomes machine-UNenforceable in the dimension the import laws stop covering: replacing 'from domain.signals import signals_table' with db.table('signals') moves coupling from the import graph (import-linter-checkable, greppable) to string keys. The registry records WRITERS (registration) but READERS are statically invisible — a component reading a downstream table, or reading before its writer runs, trips no law. Pipeline ordering now lives only in app/registry.py's run sequence, checkable by nothing. The 'map cannot lie' claim is overstated: read-edges require either fragile string-literal grepping or a declared-reads manifest the candidate does not have.
  • app/registry.py is not 'one line per phase' — it inherits the orchestrator (VERIFIED): gui/app_main.py's handlers chain multiple phases per button (line 962 imports staging, datablocks, interfaces, diagnosis, hardware, coverage plus blocks.engine in ONE handler; similar chains at 790, 827, 864, 894, 916). Since components may not import each other, every prerequisite chain must move into app/registry.py, which accretes the inter-phase run-DAG knowledge components no longer hold — a growing hotspot file at the top. Adding a typical phase edits component code AND a run-plan there, weakening 'no other file changes anywhere'.
  • The migration_cost narrative omits its largest semantic edit: extracting ~15 handler bodies out of the 1000+-line gui/app_main.py into component run_*() entrypoints plus registry run-plans, and splitting gui/phases.py (the current registry: numbers + sub-buttons + handler references bound to App methods) into app/registry vs gui/shell/phase_model. None of the five listed decoupling clusters covers this; 'gui regroup' is called mechanical but app_main is the god-object being dismantled.
  • Check-registry wiring by import side effect is fragile and invisible to every machine check: kernel/findings/checks.py is populated only if app/wiring.py imported all components first. A headless run or test that imports components/quality alone sweeps an EMPTY registry and passes vacuously — import-linter cannot see it, and the 61-file suite only catches it if tests import the app layer. Today's validation/phase.py imports its checks explicitly and fails loudly; the candidate trades that for silent under-validation.
  • components.<x>.ui discovery is necessarily dynamic (gui sits above nothing that knows the registry — app is ABOVE gui, so the shell cannot import app/registry.py): discovery must be importlib-by-string or injected callables, which import-linter cannot observe. Law 3/5's 'only the gui shell may import components.<x>.ui' is enforced against an import that never appears statically — a hole in the machine-enforced story the candidate presents as airtight.
  • kernel/vocab has no machine-enforced size bound: law 2's independence will keep convicting shared vocabulary (identity and addresses today; type_families/family_for, area vocab, script-type constants tomorrow) and the only home is the 'deliberately tiny' shelf — the flat-domain dump can reconstitute itself there with no law resisting, only convention.
  • Factual nit that survived 'grep-verified': changes/ is NOT 'all imports internal' — reader.py imports core.config and io.workbook, run.py imports core.config. Both land legally in kernel, so migration is still renames, but the candidate's verification claims should be trusted proportionally.

Strengths

  • Placement coverage is essentially total — I mapped all ~105 current pipeline4 files against the candidate and every module has exactly one home, including the unglamorous ones (core/keys.py→kernel/ssot/content_hash.py, core/run.py→kernel/gate.py, core/model.py→kernel/report/model.py, blocks/database.py→software_blocks/signals_view.py, io/xlsx_edit.py→kernel/xlsx/surgical_writer.py). No orphan found.
  • The five convicted coupling clusters are real and precisely identified (VERIFIED): blocks/engine.py:23 imports datablock_xml and :30 signals_table; fillout/fill.py:154 and :456 lazy-import staging/diagnosis; coverage.py:29 imports three builders plus identity; validation/phase.py:21-22 imports staging plus four check modules; exactly 9 modules import signals_table. The candidate's grep claims check out almost everywhere — this is a structure argued from the actual code, not from vibes.
  • Writer-owns-schema for cabinets is grounded in a subtle fact the candidate got right: staging.py:283-292 WRITES diagnosis_cabinets from the DiagnosisBlocks sheet 'so phase 600 is a pure table read', and diagnosis.py only reads it — moving the table's declaration from diagnosis_entries.py into intake is correct ownership, not guesswork.

  • All seven laws are expressible in import-linter (layers, two independence contracts, four forbidden contracts with wildcard ignore_imports for the ui/tkinter exception) — the static-contract constraint is satisfied as written, and the hard constraints are all honored: systems tree preserved and repositioned only, no phase numbers in folders (registry binds them), one dependency direction, kernel never imports tkinter.
  • The plug direction rides an existing seam: blocks/registry.py (builder_registry) already exists as the socket pattern, and io_tags.py's two dependencies (identity, signals_table) really are the only ones, making its immediate move to systems/ legal as claimed.
  • The vision story is the strongest of the constraints' fits: component __init__ as the chapter page (public API = M1 docstring = map node), kernel as 'the language of the system', systems as per-target volumes, and kernel/provenance as the peek-code substrate is a coherent, cheap-to-generate manual ToC — provided the read-edge manifest gap (breaks #3) is patched.

Migration: medium — roughly 80% of the move is mechanical (core→kernel, io→kernel, gui regroup, changes/ and fillout/ move intact, tests mirror), but the independence law immediately convicts five real coupling clusters found by grep: ~15 schema-object imports (signals_table and friends) must become kernel table-registry lookups, validation checks distribute to their owning components via a new check registry (sinking finding_factory/messages/address_parsing to kernel), and signal_coverage, document_fill, and build_engine must be re-plumbed through tables/sockets instead of importing sibling phases. These are semantic edits beyond renames, though each runs along a seam the code already half-has (builder_registry exists, ssot_database exists) — expect the 61-file suite to pass after the mechanical wave and the five decouplings to be a second, testable wave.

The laws (each an import-linter contract)

  • L1 LAYERS (import-linter 'layers'): app | (phases, workbench) | systems | shared — app may import everything below; phases and workbench may import systems and shared; systems may import only shared; shared imports nothing above it. The same contract makes phases and workbench mutually independent: a phase panel never imports a workbench tool and vice versa (they meet only through shared/ui/navigation and shared data models).
  • L2 PHASE INDEPENDENCE (import-linter 'independence' across pipeline5.phases.*): no phase slice imports another phase slice — phases communicate ONLY through SSOT tables whose schemas live in shared/tables. This is the pipes-and-filters constraint made static.
  • L3 SYSTEMS DOOR (import-linter 'forbidden'): pipeline5.app, pipeline5.phases, pipeline5.workbench must not import pipeline5.systems.plc_based.* or pipeline5.systems.ipc_based.* — the only door is systems.catalog + systems.system_contract. Active from day one, so the step-4 Siemens move changes nothing for consumers.
  • L4 KERNEL PURITY (import-linter 'forbidden', belt-and-braces with L1): pipeline5.shared must not import pipeline5.app, pipeline5.phases, pipeline5.workbench, pipeline5.systems — the kernel never knows the features or the targets.
  • L5 TOOL AND SYSTEM INDEPENDENCE (import-linter 'independence' across pipeline5.workbench.* and across pipeline5.systems.plc_based.*, pipeline5.systems.ipc_based.* subtrees): deleting a workbench tool or a target system deletes exactly one folder plus one registry/catalog line.
  • L6 TKINTER CONTAINMENT (import-linter 'forbidden' + one 15-line AST test): tkinter is importable only from app, workbench, shared.ui, and phases/*/panel.py. Enforced by a forbidden contract barring tkinter from shared.tables/expr/findings/phases/config/xlsx/tempemplator/chain_reactions and from pipeline5.systems, plus a plain-python test that walks phases/ and fails on tkinter imports outside panel.py (the per-file exception import-linter cannot express).

The critic's verdict — breaks (8) and strengths (7)

Breaks found (code-grounded)

  • Step-4 systems move breaks L1 as designed, verified in real code: pipeline5/domain/software_blocks/builders.py imports signals_view, builder_registry (->contract.py) and block_table - all of which the candidate keeps in phases/software_blocks/ permanently. Once builders.py lands in systems/plc_based/siemens_s7/, every one of those becomes a systems->phases import, forbidden by L1 ('systems may import only shared'). Step 4 is therefore not 'one git mv' - it requires re-homing block_table/signals_view/the builder contract to shared/ or inverting the builder API. The same pattern threatens diagnosis/siemens/scl_emit and the interface emitters.
  • 'L3 active from day one, so the step-4 move changes nothing for consumers' is false: before step 4, phases/datablocks/phase.py imports its own siemens/xml_doc.py directly (legal intra-slice import); after step 4 that exact call must route through systems.catalog + system_contract, which today has no datablock/hardware/interface/io_tags emission provisions. Step 4 is an interface-design event hidden inside a 'mv', and it churns the mirrored test tree a second time (tests/phases/datablocks/siemens/* -> tests/systems/*).
  • Two placement rules self-contradict, leaving a module with no honest home: L2's corollary forces EVERY SSOT schema into shared/tables ('a consumer importing a producer's schema would be a phase->phase import'), while shared/'s admission gate demands >=3 consuming slices. diagnosis_schema has producer (diagnosis) + diagcheck (crosscheck) = 2 slices. It cannot stay in the producer (L2) and fails the Rule-of-Three review for shared/. Either gate must bend, and the candidate doesn't say which.
  • Split-brain plugin seam: phases/software_blocks/contract.py is named 'the seam systems plug into', but under L1 systems cannot import it - so a Siemens builder can only satisfy it structurally (duck typing; the ABC is unenforceable on its own implementers), while systems/system_contract.py 'grows a software-block builder provision' duplicating the same seam. One contract, two homes; a builder author must consult both.
  • L6 violates the locked 'all laws import-linter/tach expressible' constraint as written: the per-file exception (tkinter allowed only in phases/*/panel.py) is admitted to need a custom AST-walking test that import-linter cannot express. Fixable by making the panel a subpackage (phases/<slice>/ui/) so a plain forbidden contract covers it - but as submitted, one of the six laws lives outside the demanded enforcement toolchain.
  • The 'mechanical mirror-move' of the test suite is not mechanical: the suite is currently FLAT (tests/unit/test_*.py, ~63 files), so mirroring means re-nesting plus rewriting imports in every file; and verified tests/unit/test_validation_standalone.py imports both iolist_checks and cematrix_checks, which land in two DIFFERENT slices - that file (and test_validation_i18n.py) must be split by hand. Also validation_runner.py:24 imports iolist_staging directly, so the crosscheck slice needs a genuine rewrite to consume the SSOT table instead of calling another phase's staging code - the 'one non-mechanical item' is bigger than admitted.
  • app/ vs workbench/ ownership ambiguity for GUI features: new_project.py (a wizard window) lives in app/ while guide/window.py (a window) lives in workbench/ - same shape of thing, two different homes. And app/ is the only package with no internal laws (it may import everything), already 9+ modules; awkward modules will gravitate there, re-forming the dump the structure set out to cure. Where does a future settings dialog or recent-projects feature go? Two defensible answers.
  • Post-step-4 hollow chapters: phases/hardware/ and phases/io_tags/ reduce to phase.py + panel.py + provenance.py with ALL logic in systems/ - the manual's 'Hardware' chapter has no body and just points at the Systems chapter, weakening 'the tree reads as the ToC' for exactly the phases that are fully target-specific.

  • L1-L5 are genuinely expressible as import-linter contracts (layers, independence, forbidden) - the pipes-and-filters rule (L2) and the systems door (L3) become static, machine-enforced facts, which is precisely the user's second pain cured.
  • The flat domain/ dump is fully cured, and cheaply mapped: I verified the candidate's 'was' list against the real current tree and it matches ~1:1 - every one of the ~25 flat domain files gets exactly one slice home, and domain/fillout, domain/changes, domain/software_blocks move as whole folders.
  • Phase growth is honestly additive: mkdir phases/<name>/ + one PhaseSpec line in app/registry.py; operator phase numbers bind in the registry per the locked no-prefix decision; L2 statically proves the new slice touched nothing else.
  • Uniform slice anatomy (phase/checks/panel/provenance) makes mapgen a single template and peek-code a deterministic artifact->slice->file lookup; because deleting a feature deletes its folder, the generated manual cannot describe a dead feature - the strongest vision_fit mechanism among plausible designs.
  • The approved systems/ taxonomy is preserved verbatim in position, with system subfolder names mirroring phase-slice names so the manual reads 'neutral phase / what each target adds'.
  • checks.py co-located with the producing table documents each gate beside its maker, and workbench tools are one-folder deletable under L5 - both directly serve the code-is-the-manual vision.
  • The registry/composition-root concession is honest and minimal: exactly one wiring file (app/registry.py) knows all slices, instead of centralized gui wiring smeared across app_main.

The laws (each an import-linter contract)

  • LAYERS (import-linter 'layers'): workbench > manual > project > phases > systems > language > documents > truth > findings > appendix. Higher parts may import lower, never the reverse; kernel parts (truth and below) can therefore never see systems or GUI.
  • CHAPTER INDEPENDENCE (import-linter 'independence'): every package directly under pipeline5.phases is independent of every other — chapters share only via truth/language/documents/findings; phases/contents.py and phases/gate.py are the only shared front-matter modules and hold no domain logic. The chapter list in the contract is regenerated and cross-checked by manual/map.py so a new chapter cannot silently escape the law.
  • PLUGIN DOOR (import-linter 'forbidden'): pipeline5.phases must not import pipeline5.systems.plc_based or pipeline5.systems.ipc_based — chapters may import only systems.contract and systems.catalog; concrete systems are reached exclusively through the catalog registry.
  • PLUGIN ISOLATION (import-linter 'forbidden' + 'independence'): pipeline5.systems must not import pipeline5.phases or pipeline5.workbench, and concrete system packages (siemens_s7, intervalzero_rtx.*) are mutually independent — a system translates truth; it never calls a chapter or another system.
  • SINGLE ENTRY (import-linter 'forbidden'): nothing imports pipeline5.workbench except pipeline5.__main__, and nothing imports pipeline5.manual except pipeline5.workbench — the manual machinery reads the whole book but only the workbench opens it.
  • GUI QUARANTINE (import-linter 'forbidden', include_external_packages=true): tkinter is importable only from pipeline5.workbench — no widget code can leak into phases, systems, or kernel.
  • BOTTOM OF THE BOOK (import-linter 'forbidden'): pipeline5.appendix and pipeline5.findings import no other pipeline5 package — they are pure reference material every part may cite.

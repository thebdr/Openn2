The Code Is the Manual

A fully open application, shipped with its own source — where every button, log line, and generated file can show you exactly how it came to be.

Drafted from the P-008/P-014 evidence · real PL5 modules used throughout · nothing here is built yet

The executable exists so nobody has to install Python. That is its entire job. The product is the open codebase — and if the codebase is the product, then the codebase must be readable the way a manual is readable: it opens where your question is, it explains itself in your language, and it never makes you guess where to look.

Help systems rot because they describe the code from outside. A manual written inside the code cannot drift from it.

1What a shipped module reads like

This is kernel/content_hash.py — the real module, its docstring rewritten as the chapter it actually is. Note the three moves: it opens with what the thing is for you, it offers a try-it, and it names where you meet it in the app — the anchors peek-code jumps through.

"""Chapter: Identity — how every signal, row, and finding gets its name.

Everything the pipeline creates carries a `uid`: a short fingerprint of the fields
that say WHAT THE THING IS — and nothing else. Not the workbook it came from, not
the row number, not the moment it was made. That restraint is the feature: re-save
the I/O List, reorder its rows, rename the file — the same signal keeps the same
uid, so everything attached to it (a treatment you set, a generated DB member,
a diagnosis bit) survives the document revision.

Try it:
    >>> uid("DI1/2", "K23", "door channel input")
    'e3a1f09b2c'
    >>> uid("DI1/2", "K23", "door channel input")   # same parts → same uid, always

Where you meet it in the app:
  · the Findings tab — every row's ID column is one of these
  · error_management.csv — your treatments are keyed by uid
  · every SSOT table — the uid column, stamped at add()

Rule of use: pass ONLY identifying fields. If a value would change when the
document is merely re-saved or rearranged, it does not belong in a uid.
"""
import hashlib

UID_HEX_LENGTH = 10   # hex chars; ample for these data volumes (inherited from PL3)


def uid(*parts) -> str:
    """A stable 10-char fingerprint of `parts`, joined by '|'. None becomes ''.
    Change or add any part and the uid changes; repeat the parts and it never does."""
    basis = "|".join("" if part is None else str(part) for part in parts)
    return hashlib.sha1(basis.encode("utf-8")).hexdigest()[:UID_HEX_LENGTH]

Nothing was dumbed down — the maintainer's precision is intact. What changed is the addressee: the docstring speaks to the person reading it inside the app, connects to what they can see on screen, and hands them something to run. Multiply by every module and the manual has written itself.

2Peek code: the manual opens where your question is

Right-click anything the app produced, and it shows you the producer. Try the log line below — this is the real staging check, with its real comment.

↳ resolves through provenance: the finding carries phase=300 + slug stg_dup_type_index → the registry lands you here, in pipeline/staging/checks.py
def _dup_type_index_findings(table) -> list:
    """Why this HALTS instead of warning: the index-grouping builders (05 Output
    Feedback, 07 Speed Control, 08 Gate Manager) treat `index` as the unit key.
    Two signals sharing (script_type, index) would be silently MERGED into one
    bogus unit — two KQ-5 contactors become a single two-contactor unit, and the
    generated logic is wrong with no error anywhere downstream. So the pair must
    be unique, and a duplicate is a raw FAIL: generation stops here, where the
    mistake is visible and clickable, not three phases later where it isn't.

    Each duplicate gets its own finding at its own I/O-List cell, naming the
    sibling cell(s) — so every one of them is individually clickable above."""

The provenance to answer every right-click already exists or is planned work: the phase registry binds buttons to handlers; findings carry their phase and slug; every SSOT table has one owning phase, and generated rows will carry spawned_by; emitters and reaction rules are registered by name. Peek-code is mostly plumbing between things PL5 already knows about itself — and when a row was spawned by a chain reaction, the peek lands on the rule in your config, not on Python at all.

3The commenting standard — six rules for manual-grade code

M1
The module docstring is a chapter. What this is for the reader, why it exists, where they meet it in the app. If the module can't say this, it isn't a module yet.
M2
Every public function is a recipe. What you get, what to pass, one runnable example when behavior isn't obvious from the signature.
M3
Comments answer why, in domain language. "Two KQ-5 contactors become a bogus unit" — never "loop over the rows". The domain is the vocabulary; syntax needs no narration.
M4
Every module declares its place in the flow. Which SSOT tables it reads, which it writes, which phase button runs it — the anchors peek-code and the map are generated from.
M5
Cross-references are links, not prose. One src:// / guide:// scheme everywhere: docstrings, the F1 guide, the log, the map — all the same resolver, already shipped in PL4.
M6
Decisions carry their history. When code embodies a choice ("blank index skipped — only indexed signals participate"), the comment says what was decided and why, so the reader never re-litigates it blind.

4The reading experience, top to bottom

Opening the code explorer lands on the map — generated from the real package tree and the signpost docstrings, so it cannot go stale. Every node opens the folder; every folder's __init__ is its table of contents; every module is a chapter. Three levels, no dead ends:

The Map ← generated, clickable, always current ├─ kernel/ the primitives every phase stands on (9 chapters) ├─ pipeline/ the phases, in the order the buttons run (13 chapters) ├─ systems/ what makes Siemens Siemens and RTX RTX (per-system books) └─ shell/ the window you are looking at (how the GUI works)

Under this vision the F1 guide keeps only the operator path — how to run a project, what a finding means. Everything deeper stops being separate documentation: the guide's "see source" links were always the honest part, and now the source is worth arriving at. The P-006 "complete the guide" mountain shrinks to a hill.

5What this costs — said plainly

Three honest prices. First: manual-grade docstrings are written and maintained by hand; the standard (M1–M6) makes them checkable in review, but nothing generates them. Second: peek-code needs the slug→site and config→consumer indexes built (small, and the registries carry most of it). Third: fully open means fully open — anyone can read, copy, and learn from the source. In this vision that is not a leak; it is the distribution model. The one guard worth keeping: the exe build pins a version stamp, so a modified copy is distinguishable from a release.

And what it saves: the structure debate deflates. When navigation happens by right-click and map, folders only need to be honest, not perfect — the enforcement contracts (phases don't import each other; one dependency direction; sealed plugins) keep the architecture sound underneath, invisibly.
